# Write endpoints with no authorization guard beyond authentication and
# organization scoping. Any authenticated member of the organization can
# call these; nothing checks which role they hold.
#
# This is a ratchet, not an approval. Adding a route here is how a new
# unguarded endpoint gets past the build, and it should be rare enough to
# be argued for. Removing one - by adding check.permission - is the point.
#
# Not everything here is a gap. Two kinds of route belong in this file for
# good:
#
#   api/v1/auth/*  — login, forgot-password, email verification and 2FA setup
#   run before there is a role to check, or act on the caller's own account.
#
#   api/v1/hr/me/* — employee self-service: own check-in, own check-out, own
#   leave request. These are scoped to the authenticated user by definition,
#   and a grantable permission on them would lock ordinary employees out of
#   their own records.
#
#   api/v1/portal/* — the customer portal, which authenticates with its own
#   session token rather than a staff JWT. Staff permissions do not apply.
#
#   api/v1/auth/impersonate/{user} — guarded, but by ImpersonationService
#   rather than by middleware, which is why it shows up here. It refuses
#   anyone who is neither a super admin nor a holder of 'impersonate_users',
#   and that permission is deliberately seeded nowhere: the seeder syncs every
#   permission to the admin role, so seeding it would hand impersonation to
#   every tenant administrator.
#
#   Anything else acting only on the caller: their notifications, preferences,
#   language, sessions, onboarding progress, default branch, and a request for
#   access to sensitive data (asking is open; granting is not).
#
# Everything else is unfinished.
